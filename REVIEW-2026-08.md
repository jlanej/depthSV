# depthSV — review notes

Review of the working tree at `7a1e385` plus the untracked `example/1000G_highcov/`.
Everything below was reproduced by running the code unless marked *(by inspection)*.
`tests/smoke_test.sh` passes 35/35 on this machine; that is the starting point, not
a defence.

**Verdict.** The engineering discipline here is genuinely above average — atomic
commits, contig names resolved from the index, a real test suite that asserts on
results. The problems are not sloppiness. They are (a) a class of silent-success
paths that PLAN.md's own principle 4 is aimed at and that the join stage already
solves correctly while the other two stages do not, (b) one estimator bug that
silently reverses published effect directions, (c) one interaction between the
`--minDepth` floor and non-normal phenotypes that manufactures genome-wide
significance while *deflating* the diagnostic you would use to catch it, and
(d) a test suite that cannot see any of it — five of eight estimator mutations
survive it, including deleting the PC correction entirely.

---

## 1. Wrong numbers that look right

These produce well-formed, indexable, plausible output with exit 0.

### 1.1 Logistic effect direction silently reverses — `R/analyze.R:218`, `:327-330`

```r
y_bin <- as.numeric(as.factor(y_vec)) - 1
```

`as.factor` orders levels by sort order, so **whichever label sorts first becomes
the modelled non-event**. A `case`/`control` column makes *controls* the event.
`NCase`/`NControl` derive from the same vector, so they swap too and stay mutually
consistent — the file contains no internal contradiction to trip over.

```
response "ybin"   (0/1):      Estimate  0.4237  z  4.163  NCase 172  NControl 228
response "status" (case/ctrl): Estimate -0.4237  z -4.163  NCase 228  NControl 172
```

Same data, same p-value, opposite sign. `conf/phenotypes.example.tsv` ships
`case_status logistic case_status~cov_resids+...` with no stated encoding
requirement, and README's input table says only "SAMPLE plus every term in your
models". Affected codings: `case`/`control`, `affected`/`unaffected`,
`Case`/`Control`, and numeric `1=case`/`2=control`. Unaffected: `0`/`1`,
`TRUE`/`FALSE`, PLINK's `1=control`/`2=case`, `Y`/`N`.

The example dodges it only by hand-recoding at
`example/1000G_highcov/R/prepare_inputs.R:69-70` — evidence the hazard is known,
not a guard against it.

**Fix:** require explicit 0/1, or take the reference level as an option, and error
on anything ambiguous. One line, and it protects the headline number of every
case/control analysis.

### 1.2 The `--minDepth` floor fabricates genome-wide significance — `R/correct.R:208`

```r
log2_ratio <- log2(pmax(opt$minDepth, depth) / median_vec)   # minDepth default 0.005
```

A zero-depth bin at 30× becomes `log2(0.005/30) = -12.55`, versus `-1.0` for a real
heterozygous deletion. In a cohort of 2,000 that single point carries **93.8 % of
the regression's leverage** (h = 0.938; mean h = 0.0005).

For a *normal* phenotype the t-test is still exact, so this is invisible. For a
non-normal one it is not:

| phenotype (null, no true effect) | λ_GC | P(p<1e-4) | P(p<5e-8) |
|---|---|---|---|
| normal | 1.01 | 0 | 0 |
| log-normal (untransformed biomarker) | **0.44** | 0.0110 | **0.0045** |
| t₃ (heavy tailed) | 0.49 | 0.0077 | 0.0026 |
| binary, 5 % cases | 0.15 | 0.0432 | 0 |

*(n = 2000, 20 000 replicate bins, one zero-depth sample each; nominal rates 1e-4 and 5e-8.)*

That is ~10⁵× the nominal genome-wide rate. On 3.1 M bins, if only 1 % carry a
zero-depth sample, that is on the order of 140 fabricated genome-wide hits.

The nastiest part: **λ goes *down*, not up.** A user checking genomic inflation
sees 0.44 and concludes the analysis is conservative.

Winsorising the log2 ratio helps but does not fix it (clamping to ±2 still leaves
P(p<5e-8) = 8.5e-4). A rank inverse-normal transform of the phenotype fixes it
completely: λ = 0.996, P(p<5e-8) = 0. Notably `R/external/analyze_nullmodel.R:22`
already documents INT as part of the GENESIS null model — the in-house linear path
has no equivalent and does not say it is needed.

**Fix:** rank-INT quantitative phenotypes by default (or refuse to run without an
explicit opt-out); add a per-region max-leverage QC; make `--minDepth` relative to
the sample's own median rather than an absolute 0.005 in raw depth units — as
written the floored value encodes the sample's *sequencing depth*, not its copy
number (−9.97 at 5×, −13.55 at 60×).

### 1.3 `.done` markers are keyed on a filename that omits almost every parameter

`scripts/correct.sh:56` names outputs `corrected_ndim{N}.{region}.txt.gz`;
`scripts/analyze.sh:98` names them `{name}.{method}.{region}.txt.gz`. Everything
else is invisible to the skip logic. Demonstrated:

```
run 1: myphen  linear  quant_trait~cov_resids
       chr1:0-1000   Estimate 0.68803367   p 0.37450434

run 2: myphen  linear  quant_trait~cov_resids+age+sex+ancestry_PC1+ancestry_PC2
       "already complete, skipping: myphen.linear.chr1.txt.gz"
       chr1:0-1000   Estimate 0.68803367   p 0.37450434     <- never fitted
```

Same for swapping the entire phenotype table, and for `correct.sh` with a
completely different coverage table (halving every median — every log2 ratio should
shift by exactly +1; output was byte-identical).

Not encoded anywhere: the model formula, `--pheno`, `--pcs`, `--coverage`,
`--corrected`, `--minObs`, `--minVariance`, `--minDepth`, `--projection`,
`--sampleIdPattern`, `--digits`.

The consequence at scale (`workflows/slurm_array.sh`, `example/.../02_run_depthsv.sh`):
run the genome at `DSV_NDIM=16`, inspect the correction statistics, decide 30 is
right, resubmit. `correct.sh` writes fresh `corrected_ndim30.*`; `analyze.sh` finds
the ndim=16 `.done` markers and skips every region. The summary statistics are
from ndim=16 while the corrected matrix on disk says ndim=30.

**`scripts/join.sh` already does this correctly** — `resume.meta` (join.sh:112-122)
records a cksum of the manifest plus the batching parameters and invalidates on
mismatch. The mechanism exists; it just was not applied to the other two stages.

**Fix:** write a sidecar `.params` next to each `.done` holding a hash of every
input path + mtime + every parameter, and treat a mismatch as "not complete".

Two adjacent variants:

- **`--force` that fails leaves the old result and its `.done` in place.**
  `correct.sh:63` / `analyze.sh:105` call `dsv_output_reset`, which by contract
  (`lib/common.sh:149-154`) deletes nothing while `.done` exists. `join.sh:72-75`
  explicitly `rm -f`s the marker under `--force`; the other two do not. Resubmitting
  a partially-failed forced array without `--force` — which `slurm_array.sh:18-19`
  documents as the recovery procedure — silently returns pre-force results.
- **Two models colliding on one output path.** `analyze.sh:166` defaults the name
  to the response variable, so `y~cov_resids+age` and `y~cov_resids+age+sex` both
  resolve to `y.linear.{region}.txt.gz`.

### 1.4 `--sampleIdPattern` can map two matrix columns to one participant — `R/correct.R:116`, `R/analyze.R:117`

`match()` is many-to-one and nothing checks the *matrix-side* IDs for duplicates.
`join.sh:85-91` refuses duplicate sample names but only *before* the pattern is
applied; `analyze.R:95-101` refuses duplicate `pheno$SAMPLE` — with a long comment
explaining exactly why duplicates misalign — but never duplicate `sample_ids`.

Reproduced with the scenario README:251 itself suggests the flag for (a participant
sequenced twice):

```
20 participants -> 40 mosdepth files (SAMPLE001_run1, SAMPLE001_run2, ...)
join.sh:      exit 0, 40 columns
correct.sh --sampleIdPattern '(SAMPLE[0-9]+)_run[0-9]':  exit 0, 40 columns,
             20 duplicated column names
analyze.sh:  exit 0,  [align] samples=40 usable=40,  N reported = 40
```

Every participant contributes twice with a perfectly duplicated row. SE deflated
by √2, p-values correspondingly inflated. No warning at any stage.

**Fix:** `anyDuplicated(kept_samples)` in `correct.R` and `anyDuplicated(sample_ids)`
in `analyze.R`, mirroring the guard that already exists on the phenotype side.

### 1.5 The default join checks row *counts* only — `lib/join_extract.sh:39-42`

Without `--strict-coords` the only cross-sample check is `rows -ne expected`. Any
two inputs with the same bin set in a **different order** — realistically, mosdepth
run against a lexicographically-ordered `.fai` versus a karyotypically-ordered one —
pass and are pasted misaligned. Every downstream stage then attributes those depths
to the wrong coordinates, and the result is a well-formed, correctly-row-counted,
tabix-indexed matrix. Verified end-to-end by an independent reviewer.

`--strict-coords` is opt-in because it decompresses each file a second time
(`join_extract.sh:45`). It does not have to: the coordinate columns are already
being read at line 36, so the checksum can be computed in the same pass with `tee`
or a single `awk`. Then it can be the default.

Related, *(by inspection + reviewer repro)*: `join.sh:242`'s column-count check
cannot detect a **short column** either, because `paste` emits the full separator
run for an exhausted input — `NF` is invariant to it, and `dsv_output_commit`'s
row-parity check compares against `ref_rows`, which the coordinate file alone
already satisfies. A bgzf file truncated at a block boundary decompresses cleanly,
exits 0, and pads the rest of the matrix with empty fields.

### 1.6 `analyze.sh`'s worker pipeline swallows R's exit status — `scripts/analyze.sh:129`

```sh
worker="cat $hdr - | Rscript $rscript ... 2>>$log | tail -n +2"
```

GNU parallel sees `tail`'s status, never `Rscript`'s:

```
$ printf 'a\nb\nc\n' | parallel --pipe -k --halt now,fail=1 -j2 'cat /dev/null - | sh -c "cat; exit 1" | tail -n +2'
exit=0        <- failure invisible

$ (same, without the trailing pipe)
exit=1        <- detected
```

`analyze.sh:123-125` explicitly declines a row-parity check on the grounds that
"completeness is enforced by `--halt now,fail=1` plus the integrity check in
`dsv_output_commit`". Neither holds: `--halt` cannot see the failure, and
`dsv_output_commit` called without an expected count only runs `bgzip -t` and
`tabix`, which both pass on a truncated-but-well-formed file. An R crash part-way
through a region silently drops that chunk's rows and writes a `.done` marker.

`correct.sh`'s worker has no trailing pipe *and* does pass a row count — the
asymmetry is the tell.

### 1.7 `join.sh` "already complete" ignores the manifest — `scripts/join.sh:68-71`

`dsv_output_complete` is checked *before* the `resume.meta` manifest-signature
comparison (join.sh:112-122), which is never consulted for this case.

```
joined 30 samples -> matrix has 30 sample columns
re-ran with the 60-sample manifest -> "already complete, skipping"
                                   -> matrix still has 30 sample columns, exit 0
```

Adding samples to a cohort and re-running silently analyses the old half.

### 1.8 `regions.sh --sizes` silently decides which genome gets analysed — `scripts/regions.sh:77-88`

The region list is the intersection of the tabix contig list and `--sizes`,
by **exact string match** (`present[$1]`), bounded by the recorded length. A contig
absent from `--sizes`, given a short length, or named in the other convention is
silently dropped — exit 0, empty stderr. README:180-183 tells the user to pass
`hg38.chrom.sizes`; `lib/common.sh:119-125` goes to some trouble to accept either
naming convention everywhere *else*, so a UCSC sizes file against an Ensembl-named
matrix yields an empty or partial region list with no complaint.

### 1.9 The environment overrides the flag the user typed — `scripts/analyze.sh:59-60`

```sh
[ -z "$min_obs" ] || extra+=(--minObs "$min_obs")       # env value appended AFTER
[ -z "$min_var" ] || extra+=(--minVariance "$min_var")  # the user's -- passthrough
```

optparse keeps the last occurrence, so the env wins. `conf/example.env:7` and
README both state the opposite contract ("Flags always win over the environment").

```
$ DSV_MIN_VARIANCE=1e9 analyze.sh ... -- --minObs 30 --minVariance 0
exit 0,  0 result rows,  .done written,  [done] processed=0 skipped=200
```

### 1.10 One `NA` in the coverage table empties the whole genome, exit 0

`R/correct.R:79` uses `pmax(opt$minDepth, AUTO_HQ_median)` with `na.rm = FALSE`, so
an NA median survives. One NA in `median_vec` puts one NA in `log2_ratio`, and the
matrix product in `residualize()` (correct.R:170) propagates it to **every column**:

```
coverage row 2: SAMPLE001  NA          (1 of 60 samples)
correct.sh  exit 0   "row parity ok: 200 rows"   [done] processed=200 samples=60
            first data row: NA NA NA ... (60 of 60)
analyze.sh  exit 0   0 result rows   .done written
            [align] samples=60 usable=60   [done] processed=0 skipped=200
re-run:     "already complete"
```

Both stages green, output well-formed and tabix-indexed, no `[warn]` (the NA is in
a reference table, not a data row). This composes three separate defects into one
silent whole-genome null and is a direct violation of PLAN.md principle 4.

More generally: **`analyze.sh` commits a header-only result with a `.done` marker
and exit 0.** Verified with `--minVariance 1e9`. Over a 140-unit array, a mis-set
threshold produces 140 valid empty shards and a green run.

## 2. The method

### 2.1 The PC-correction cliff — the central scientific caveat

The PCs are computed from the depth matrix that is then residualised against them.
Whether a CNV survives is a **step function** of its variance rank, not a gradient.
With a realistic PC spectrum (n = 1000, 5000 bins, 60 decaying latent technical
factors, a 20-bin deletion at AF 0.20 whose axis lands at PC61):

| ndim | median \|t\| | median −log10 p | power @ 5e-8 |
|---|---|---|---|
| 0 | 3.3 | 2.9 | 0 % |
| 16 | 5.5 | 7.4 | 50 % |
| 32 | 7.8 | 13.9 | 100 % |
| 58 | 10.8 | 25.0 | 100 % |
| **60** | **11.0** | **25.9** | **100 %** |
| **62** | **0.8** | **0.4** | **0 %** |
| 200 | 0.6 | 0.3 | 0 % |

Two more components and a 25.9 turns into a 0.4. Below the cliff the correction
*helps* — it removes technical noise the CNV does not live in. Above it, the signal
is gone completely, and nothing in the output distinguishes "absent" from "removed".

This is not a bug; it is inherent to the design. But:

- The default is `--ndim 16` / `DSV_NDIM=16`, and PLAN.md:148-151 records ndim=200
  as validated at scale, caveated with *"where copy-number variants are not a
  primary source of variation"*. That caveat is doing all the work, it is exactly
  what fails for a common CNV, and there is **no way from the pipeline's outputs to
  check whether it holds for your cohort**.
- The project has already hit this. `example/1000G_highcov/config.sh:78-88` measures
  the leading PCs explaining R² ≈ 0.67 of MTDNA_CN and drops `EX_NDIM` from 20 to 4
  for smoke runs so the checks still fire. That is the same phenomenon on a
  phenotype instead of a locus, and it is documented in a config comment rather
  than in README's methods.
- The reported effect size is a PC-conditional estimand. β̂ is unbiased for the
  full-model β by Frisch–Waugh (I checked; calibration also holds under the null,
  λ ≈ 1.0 even when the phenotype is 49 % explained by PC1 — see §7), but "the log2
  effect of this bin" is not what is being estimated once ndim dimensions are gone.

**Fix:** emit, per region, the fraction of variance the correction removed (the
pre/post stats file at `correct.sh:57` almost does this and nothing reads it); and
run the sweep at two ndim values and report the difference — a signal that moves is
a signal the correction is eating.

### 2.2 No region-level artifact filter — `R/analyze.R:308-312`

The complete per-region QC is `--minObs` (default 100) and `--minVariance`
(default 1e-12, i.e. "not literally constant"). Both are *floors*. There is no
mappability filter, no GC correction, no segmental-duplication or centromere
exclusion, no per-region call rate, no maximum-variance or leverage cap, and no
blacklist. At 1 kb over hg38 the bins whose depth is a near-pure function of
library prep and aligner behaviour rather than copy number are exactly the bins
with the largest cross-sample spread — i.e. the ones that will top the hit list.
Combined with §1.2 this is the most likely route to a wrong published locus.

### 2.3 Sex chromosomes and chrM — `R/correct.R:208`

Every contig is normalised by the sample's autosomal median, with no branch on
contig, no PAR handling, no ploidy model. A chrX non-PAR bin reads ≈ −1 in males
and ≈ 0 in females: a perfect, genome-scale sex indicator. `conf/phenotypes.example.tsv`
includes `+sex` in every model — which is what saves it — but nothing explains that
this is load-bearing, and `example/1000G_highcov/01_prepare_inputs.sh:64-68` ships
models with **no covariates at all** (`MTDNA_CN~cov_resids`). Any phenotype
correlated with sex will light up chrX/chrY end to end.

### 2.4 Complete separation is reported as a null result — `R/analyze.R:252-266`

`fit_logistic` wraps `glm.fit` in `suppressWarnings` and gates only on
`is.finite(beta) && is.finite(se)`. Under (quasi-)complete separation the MLE
diverges, β and SE both blow up but stay finite, and the Wald z collapses toward
zero (Hauck–Donner) — the strongest real effect in the genome reports the weakest
statistic and a p near 1. `f$converged` is available and unused; there is no
convergence column in the output. `example/1000G_highcov/R/evaluate.R:172-187`
documents the collapse as expected behaviour, which is right, but the pipeline
gives a downstream reader no way to tell a collapsed fit from a true null.

### 2.5 There is no calibration or completeness output

Nothing in `scripts/` or `R/` reports λ, an effective number of tests, or a
significance threshold; and nothing concatenates the per-region shards or verifies
that the shard set covers the matrix. README:21 puts aggregation out of scope and
README:192 tells the user to concatenate — so a work unit that dies leaves a
genome-wide hit list quietly missing 25 Mb, with no file, log or manifest recording
the gap. The example's `evaluate.R:105-111` does compare shard count to unit count,
but only as a WARN and only inside the example.

Given §1.2, note that λ is *not* a sufficient diagnostic here — it reads deflated
in exactly the case that matters.

## 3. Hard blockers at the documented production settings

### 3.1 The stats merge fails at ≥10 chunks and the region can never complete — `scripts/correct.sh:124-127`

```sh
head -n 1 "$(ls "$stats_dir"/stats.*.txt | head -1)" > "$stats"
for f in "$stats_dir"/stats.*.txt; do tail -n +2 "$f"; done >> "$stats"
bgzip -f "$stats" && tabix -f -p bed "${stats}.gz"
```

The per-chunk files are named by GNU parallel's `{#}`, so the glob is lexicographic:
`stats.1, stats.10, stats.11, ..., stats.2`. From 10 chunks on, the merged BED is
coordinate-unsorted:

```
[E::hts_idx_push] Unsorted positions on sequence #1: 129001 followed by 10001
tbx_index_build3 failed
```

Under `set -e` that kills `correct.sh` at line 127 — **before** `dsv_output_commit`
at line 131 — so the whole region's correction is discarded and the failure is
deterministic on re-run. Chunk count is `ceil(region_bytes / DSV_BLOCK_BYTES)`, so
≥10 chunks is the normal case at realistic sizes. The smoke test runs 2 chunks.

**Fix:** `sort -V` / zero-pad the chunk index, or `sort -k1,1 -k2,2n` before bgzip.

### 3.2 `regions.sh` requires a writable matrix directory — `scripts/regions.sh:68`

```
regions.sh: line 68: .../ro/.dsv.contigs.21800: Permission denied
```

Fails on a read-only reference share or a WDL-localised input. Use `mktemp` in
`TMPDIR`.

### 3.3 `dsv_output_commit` assumes `.tbi` — `lib/common.sh:180-183`

`tabix -f -p bed` refuses coordinates beyond 2²⁹ ("Try using a csi index") and the
subsequent `mv "${tmp}.tbi"` has no `.csi` branch, even though `dsv_output_reset`
already cleans one up. Not an issue for human assemblies; a hard wall for anything
with a contig over 537 Mb.

## 4. What the test suite actually proves

35/35 pass. Independent mutation testing against a clean checkout:

- **`R/correct.R:138` → `use_resid <- FALSE`** (delete the PC correction entirely):
  smoke test still `passed 35, failed 0`; example CI job still exit 0.
- **5 of 8 estimator mutations survive** the full suite.
- **coxph has zero numeric assertions anywhere.** `smoke_test.sh:150-151` checks a
  row count; the example's manifest contains no coxph row. `R/analyze.R:268-276` is
  verified by nothing.
- **The λ gate cannot fail.** `smoke_test.sh:184` accepts 0.6–1.6 over 400 null
  tests; simulation puts the pass rate at 99.2 % when every test statistic is
  inflated 10 % (λ ≈ 1.22) and 82 % at 20 % inflation. At λ = 1.22 on 3.1 M bins
  that is roughly a 5× excess of genome-wide hits sailing through CI.
- **Nothing asserts the value or sign of any estimate**, so §1.1's sign inversion
  is structurally invisible: `ncase_lt_ncontrol` and `ncase_plus_ncontrol_eq_n` both
  still hold under inversion.
- The rank-deficiency check (`smoke_test.sh:276-283`) never calls depthSV code — it
  re-derives the projection inline, so removing the rank truncation from
  `correct.R`/`analyze.R` passes.
- The fixtures have no zero-depth bins, no missing values, no sex chromosomes, no
  non-numeric fields, uniform bin sizes, and 60 samples — the entire robustness
  surface of both R scripts is unexercised.

Harness bugs: `bad_log` returns non-zero as the last command of a `||` list, so
under `set -e` a stage failure with an empty log aborts the suite mid-run and the
`passed N, failed M` summary never prints (reproduced). `rm -rf "$work"` at line 20
runs on an unvalidated `$1`.

## 5. `R/external/analyze_nullmodel.R`

README:311-317 presents this as "what exists today". CI only *parses* it; there is
no wrapper, no test, no fixture.

- **The scalar `cholSigmaInv` case is unhandled and fails every region, exit 0.**
  GENESIS stores `cholSigmaInv` as a length-1 numeric for a homogeneous-variance
  model. `calcGtilde` has a `length(C) == 1` branch; this file (`:89`, `:97`, `:217-218`)
  does not. `tC %*% G` returns a 1×N *row* matrix, line 218 then fails
  non-conformably for every region, the `tryCatch` counts it as an error, and the
  script emits a header-only file and exits 0. Reproduced against a
  GENESIS-shaped null model.
- **`var(G[obs]) == 0`** (`:213`) is exact float equality with no tolerance option,
  where `R/analyze.R:312` uses `<= minVariance`. ULP-flat regions emit p ≈ 1e-31.
- **No duplicate check on the header sample IDs** (`:155`), so `G[nm_target] <- ...`
  silently assigns one sample another's depth — same class as §1.4.
- **`--sampleIdPattern` does not exist here**; the knob is the undocumented
  `DSV_SAMPLE_ID_PATTERN` environment variable (`:145`), absent from
  `conf/example.env`.
- `family` and `hetResid` are read and never used, so the binary/GMMAT path only
  *looks* handled.

Either wire it into the suite with a synthetic null model, or mark it explicitly
unvalidated in README.

## 6. Documentation vs code

- **README:177 documents a 0-based `--region` form** (`chr1:0-10000000`) that
  duplicates one bin at every boundary. `regions.sh:71-86` deliberately emits
  `[s+1, s+w]` precisely to avoid that, and explains why in a comment. The two
  contradict each other, and `smoke_test.sh:131` uses the 0-based form.
- **`regions.sh --window`'s partition guarantee is conditional** on every bin
  matching the width of the file's *first data row* (`regions.sh:60`, `NR==2`).
  Constructed a 12-row matrix with mixed 1000/1500 bp bins: windows returned 13
  rows, `chr1:9500` in both. README:186-188 states the guarantee unconditionally.
- **`--chunk` is not "maximum rows handed to one worker".** Under `--pipe`, `--block`
  governs: asking for `-L 100` on a 140 MB stream gave jobs of **19,100 lines**.
  Worker count is `ceil(bytes / DSV_BLOCK_BYTES)`, so `--jobs` is inert for any
  region smaller than `jobs × 64 MB` of decompressed text. `lib/common.sh:205-210`
  also claims the explicit `--block` "avoids that regrow entirely"; it does not —
  parallel still warns and regrows when one record exceeds the block.
- **"scratch stays near two batches of columns"** (README:100-104) omits that every
  compressed batch accumulates until the final fan-in, so peak scratch is the whole
  compressed matrix plus two batches.
- **Six quantitative claims have no reproducer in the repo** — "12–20× faster at
  25,000 samples", "agrees with qr.resid to ~6e-14", "linear and logistic agree to
  ~1e-13", "the correction is exact against an independent recomputation",
  "byte-identical to the original implementation", and "Results are byte-identical
  between the container and a host run" (the CI `container` and `smoke` jobs run
  independently and never compare outputs). These are assertions about work done
  elsewhere. PLAN.md:24 — *"the current numbers are the specification"* — makes the
  whole verification argument agreement-with-the-previous-implementation, which
  cannot catch a sign error that was always there.
- Undocumented flags the code accepts: `--minDepth`, `--digits`, `--statsFile`,
  `--skipOutputHeader`. `--minDepth` in particular changes the log2 ratio README
  describes.
- README never states that the depth term must be literally named `cov_resids`
  outside the `conf/` comment.
- `lib/common.sh:200` hardcodes the `.by1000` suffix in `dsv_sample_name` — the one
  function the join driver and its worker must agree on — while PLAN.md:135-138
  lists bin size as an open decision. `SAMPLE.by5000.regions.bed.gz` yields the
  sample name `SAMPLE.by5000`, and `correct.R:118` then dies with
  "no matrix sample matched the PC/coverage tables; check --sampleIdPattern",
  pointing at the wrong cause.
- `example/1000G_highcov/config.sh:21` dies under `set -u` when `USER` is unset
  (containers, cron, `env -i`): `config.sh: line 21: USER: unbound variable`.
- The CI `example` job fetches from `raw.githubusercontent.com` at ref `master` —
  a moving target, so the truth checks are not reproducible and CI depends on a
  third-party repo's HEAD.
- `example/1000G_highcov/00_fetch_inputs.sh:144-147`: in a *real* run with no local
  NGS-PCA output, the GitHub fallback pairs the user's **local** mosdepth depths
  with the **committed run's** PCs and coverage medians. 1000G IDs match, so nothing
  is dropped and nothing warns.

## 7. Checked and *not* a problem

Recording these so they don't get re-litigated:

- **The two-stage design is calibrated.** Residualising depth against PCs while the
  PCs are absent from the association model does not inflate type-I error, even
  when the phenotype is 49 % explained by PC1 (λ_pipeline 0.983 vs λ_fullmodel 0.978;
  P(p<0.05) 0.0478 both). β̂ matches the full-model β by Frisch–Waugh. The SE is
  inflated relative to a full model by the PC-explained variance in y, so the test
  is *conservative* — a power cost, not a validity problem.
- **The `--minDepth` floor does not break a normal phenotype.** The t-test is exact
  regardless of how leveraged x is when y is normal (λ = 1.007, tail rates nominal).
  The failure in §1.2 is specific to non-normal y.
- **`sort` is not locale-sensitive here.** The zero-padded numeric prefix in
  `%06d_%s` dominates under both C and en_US.UTF-8, so join column order is stable.
- **The `explicit` vs `qr` projection equivalence holds**, including the rank
  truncation, and the smoke test does check it.
- **A 5-column mosdepth file (`--by <named BED>`) does not silently corrupt.**
  `join_extract.sh:36`'s `cut -f4` takes the BED *name* column and the join accepts
  it, but `correct.sh` then dies with "incomplete output: 0 body rows, expected 50".
  Loud — just after the whole join, and pointing at the wrong stage. A numeric check
  on the first value in `join_extract.sh` would move it to second 1.
- **`join.sh:242`'s short-row diagnostic is unreachable on a large matrix.** `awk`
  exits early, `bgzip` takes SIGPIPE, and under `pipefail` the assignment dies with
  141 before the check runs (reproduced). The run still fails and promotes nothing,
  so this is diagnostic quality, not correctness — but it works in tests and fails
  in production, which is the wrong way round.
- p-values underflow to a literal `0` above |t| ≈ 38.5. The test statistic is
  emitted alongside, so it is recoverable; worth a `LOG10P` column at biobank scale.
